# Общий API сайта и приложения — 2.1.0

Дополнение 2.4.1: API входа и форматы токенов AA ID не меняются. Сервер
сохраняет обновлённые cookie Pulse и упреждающе продлевает SSO по отдельному
таймеру, который успешные проверки профиля и Set-Cookie не откладывают.
Это не гарантия бессрочного входа:
отзыв и максимальный срок контролирует МИРЭА. Клиент не принимает и не публикует
cookie, а продолжает штатно обновлять access-токен AA ID своим refresh-токеном.
`label` автоматически заполняется из собственного профиля МИРЭА, если оставлена
заглушка. Пользовательское имя не заменяется; берите итоговое значение с сервера.

Дополнение 2.2.0: `GET /site/state?lesson_start=<Unix seconds>` выбирает пару
из `available_lessons`, `POST /site/mark` принимает тот же `lesson_start`.
Окно — от −30 минут к началу до +30 минут к концу включительно; сервер
проверяет его повторно. При `409` обновите state и предложите допустимую
пару. `lesson`/`next` сохраняют прежнее значение; для выбранной используйте
`selected_lesson`. Строки дневной таблицы берите из `people`, а отметки —
строго из соответствующего `lessons[i].marks`/`mirea`; отсутствующий ключ
рисуется прочерком. Не переносите отметку в соседний столбец. При `401`
нужен новый вход: сервер проверяет отзыв AA ID и текущую группу.
Полный контракт — [API.md](API.md).

Приложение выполняет те же действия и получает те же серверные представления,
что сайт. Сервер хранит Pulse-cookie, browser storage и результаты операций;
приложение получает только собственные AA ID access/refresh-токены.
Новые внешние запросы и отдельная логика Pulse для приложения не добавлены.

## Несовместимые изменения

Следующие маршруты удалены и возвращают `404`:

| Старый маршрут | Замена |
| --- | --- |
| `POST /v1/auth/mirea` | Серверный QR-вход, описанный ниже |
| `POST /api/accounts/import` | Подключение аккаунта сервером после QR-входа |
| `POST /api/accounts/{id}/rpc/{method}` | Готовые JSON-операции сайта |
| `PUT /api/accounts/{id}/pass` | Клиент больше не публикует номер пропуска |
| `POST /api/debug/pass-testing` | Удалён; ежедневный тестовый ключ больше не выдаётся панелью |

С 2.3.0 цифровой пропуск подключается серверными JSON-операциями:
`POST /site/pass/code`, затем `POST /site/pass/issue` с `{"code":"012345"}`.
Выпуск разрешён только владельцу аккаунта; клиент не передаёт номер, cookie
или Pulse-токен. Приложение использует AA ID Bearer, сайт `/passes` — cookie.
`GET /site/passes` возвращает доступные карточки без номеров;
`GET /site/passes/{id}` выдаёт один сохранённый номер строкой либо `null`.
Для чужого пропуска нужны включённый `pass_allowed`, явное разрешение владельца
и текущая видимость группы. Разрешение не даёт права перевыпуска.
Выключенный `pass_allowed` запрещает выдачу, отправку кода и выпуск даже владельцу.
При отзыве или выходе очистите номер из памяти; не сохраняйте его на устройстве
и проверяйте доступ перед каждым использованием. Сервер не может отозвать уже
скопированные клиентом байты или гарантировать принятие пропуска турникетом.
Старые RPC и публикация номера остаются закрыты; существующее приложение
необходимо перевести на эти маршруты. Полный контракт и ошибки — в [API.md](API.md).
Управление разрешениями владельца, запросами доступа и списком людей сохранено.

`GET /api/accounts` сохраняет авторизованный снимок метаданных, но больше не
возвращает `passes`, номера цифровых пропусков и поля режима тестирования.
`GET /api/events` остаётся каналом уведомлений о разрешённых изменениях.
Исторические значения в БД не удаляются; обновление не требует повторного импорта.

## QR-вход приложения

1. На `https://aaid.ytc-srv.org` вызвать `POST /v1/auth/logins` без тела.
   Ответ: `{"id":"...","token":"..."}`. `token` — секрет задания входа.
2. Опросить `GET /v1/auth/logins/{id}` с `X-Login-Token: token`.
   Ответ содержит `status`, `error`, `qr` и `qr_png`, как на сайте.
   Показывать `qr_png` пользователю. QR подтверждается штатным способом MIREA.
3. После `status=complete` вызвать `POST /v1/auth/logins/{id}/claim`
   с тем же `X-Login-Token`, без клиентских cookie Pulse и browser storage.
4. Ответ содержит `access_token`, `access_expires_at`, `refresh_token`,
   `session_id`, публичный `user` и `linked`. `linked=false` означает, что
   AA ID-вход выполнен, но передача сессии основному серверу не удалась;
   приложение должно показать это пользователю, а не импортировать сессию само.
5. Повторное получение результата задания запрещено. Неверный секрет даёт
   `404`, незавершённое или уже использованное задание — `409`.
6. Обновлять токены через `POST /v1/auth/refresh`; завершать сессию через
   `POST /v1/auth/logout` или общий `POST /web/logout` с Bearer.

Веб-сайт продолжает использовать `/web/logins` и cookie `aaid_web`.
Оба способа вызывают один процесс QR-входа, привязки и серверного сохранения
учётных данных. Для приложения не создаётся браузерная cookie.

## Общие операции

На основном сервере `https://aa.ytc-srv.org` приложение передаёт
`Authorization: Bearer ACCESS_TOKEN` в те же обработчики, что использует сайт:

| Маршрут | Действие |
| --- | --- |
| `GET /site/state` | Текущая/ближайшая пара, люди, состояния отметок |
| `GET /site/today` | Сегодняшние пары и отметки; `/api/me/today` остаётся алиасом |
| `GET /site/schedule` | Недельное расписание, те же параметры group/week/name |
| `GET /site/schedule/search` | Поиск группы |
| `POST /site/mark` | Отметка по QR: qr, account_ids, own_group |

Клиент выбирает действие и людей, но не задаёт результат отметки, номер
занятия в произвольном protobuf или чужую личность. Сервер определяет группу,
текущую пару, доступный круг людей, формирует RPC и сохраняет ответ Pulse.
Запрос с человеком вне разрешённого занятия отклоняется до вызова Pulse.

На AA ID те же маршруты `/web/account`, `/web/username`, `/web/people`,
`/web/pass`, `/web/passes`, `/web/pass/people`, `/web/pass/requests`,
`/web/attendance`, `/web/schedule`, `/web/me`, `/web/sessions/{id}`
теперь принимают также Bearer приложения. Формы JSON и проверки прав общие
с сайтом. Изменения `/web/account` по-прежнему используют PUT; запросы
разрешений — POST, отзыв разрешений и сессий — DELETE.
Явный неверный Bearer не подменяется действующей cookie.

## Доверие к данным

- `label`, `username`, `pass_allowed`, выбор людей и разрешения — намерения
  пользователя, проверяемые сервером на формат и право изменения.
- Группа и личность берутся из проверенной AA ID-сессии/подписанного токена.
- Во внутреннем handoff группа и её название берутся из подписанных claims,
  а не из одноимённых полей JSON.
- Pulse-cookie и browser storage передаются только между серверными сервисами
  по отдельному audience `aa-link`; обычный токен приложения для этого непригоден.
- На клиенте остаются токены доступа и отображаемые данные; он не является
  источником подтверждённого состояния университета.

Старое приложение нужно обновить до перехода на 2.1.0. Возвращать старые
методы через nginx или включать обход проверок для совместимости не следует.
