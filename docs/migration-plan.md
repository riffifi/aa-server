# План переноса функционала с приложения на сервер

Документ описывает, как перенести логику из клиентского приложения
(`riffifi/antiattendance`, Flutter) на серверную сторону (`riffifi/aa-server`,
FastAPI), чтобы повысить безопасность, и какие улучшения стоит сделать попутно.

## 1. Зачем это нужно (принцип)

Сейчас приложение — «толстый клиент»: оно хранит на телефоне рабочие сессии
Пульса (cookie во `flutter_secure_storage`), само ходит в Пульс и умеет
переносить сессии между телефонами. Любой телефон с приложением — это копия
учётных данных, которую нельзя ни отозвать централизованно, ни проконтролировать.

Цель переноса: **сервер становится единственным доверенным местом, где лежат
учётные данные и выполняются операции с Пульсом**. Телефоны (и веб, и бот)
становятся тонкими клиентами без постоянных секретов. Это даёт:

- один набор секретов вместо N копий на устройствах;
- централизованный отзыв доступа (завершение сессии, удаление);
- единые лимиты, аудит и мониторинг;
- отсутствие переносов «сырых» cookie между устройствами.

## 2. Что уже на сервере

На сервере уже реализовано (и это фундамент миграции):

- хранение сессий в зашифрованном виде (Fernet) + `master.key`;
- вход через МИРЭА (QR) серверным headless-браузером и авто-продление;
- прокси разрешённых Пульс-RPC (профиль, подтверждение, пропуск) — телефон не
  видит cookie, а отправляет запрос через сервер;
- самообслуживание: персональная страница `/u/{id}` под паролем, вход через
  университет, Telegram-бот (уведомления, продление, enrollment);
- автоопределение группы, индикатор посещения (турникеты), управление в админке.

То есть прокси-модель уже есть. Миграция — это «добить» её до состояния, когда
на телефоне **не остаётся ничего, что имеет ценность при краже**.

## 3. Инвентаризация: что переносить

| Функция в приложении | Где секрет сейчас | Куда переносим | Приоритет |
|---|---|---|---|
| Хранение сессий Пульса | телефон (secure storage) | только сервер (уже есть) | — |
| Подтверждение присутствия по QR | телефон → Пульс | телефон → **сервер** → Пульс (прокси, есть) | высокий |
| Выпуск/проверка пропуска | телефон → Пульс | сервер-прокси (есть) + разрешение владельца (есть) | высокий |
| Перенос сессий между телефонами (Nearby/QR) | телефон → телефон | **убрать**: доступ даёт сервер по аккаунту | высокий |
| Расписание/группа | телефон → schedule API | сервер отдаёт из кэша группы (частично есть) | средний |
| История посещений | локально на телефоне | сервер (из ACS-таймлайна, есть) | средний |
| Проверка обновлений/релизы | телефон → GitHub | остаётся на клиенте (не секрет) | низкий |
| Диагностика NFC/турникета | только телефон (железо) | **остаётся на телефоне** (нужен аппаратный NFC) | — |

Важно: часть вещей физически не переносится — работа с NFC-железом и Observe
Mode завязана на телефон. Это не секреты, их можно оставить на клиенте.

## 4. Целевая архитектура

```
┌─────────────┐     HTTPS(+токен сессии страницы)      ┌──────────────────┐
│  Веб-ЛК /u  │ ───────────────────────────────────▶  │                  │
│  Telegram   │ ───────────────────────────────────▶  │   aa-server      │  Fernet-хранилище
│  Тонкий     │ ───────────────────────────────────▶  │  (FastAPI)       │  master.key
│  клиент(тел)│                                        │                  │
└─────────────┘                                        └───────┬──────────┘
      ▲  никаких постоянных cookie Пульса                      │ cookie Пульса
      │  только короткоживущий токен доступа к серверу         ▼
                                                        ┌──────────────────┐
                                                        │  pulse.mirea.ru  │
                                                        └──────────────────┘
```

Телефон в целевой схеме держит только **токен доступа к нашему серверу**
(короткоживущий, отзываемый), а не cookie Пульса. Все обращения к Пульсу идут
через сервер. Украденный/потерянный телефон отзывается одним действием на
сервере, cookie Пульса при этом не утекает.

## 5. Поэтапный план (каждый этап самодостаточен)

**Этап 0 — то, что уже сделано.** Серверные сессии, прокси RPC, веб-ЛК под
паролем, бот, автопродление, группа, посещение. Отправная точка.

**Этап 1 — завершение сессии (в этом же релизе).** Кнопка «Завершить сессию» в
веб-ЛК и в админке: сервер обнуляет сохранённые cookie/состояние браузера,
помечает аккаунт просроченным и (best-effort) дёргает logout Пульса, чтобы убить
SSO-сессию и на стороне МИРЭА. Это база централизованного отзыва.

**Этап 2 — токены доступа устройств вместо cookie на телефоне.** Ввести
серверные «device tokens»: телефон получает короткоживущий отзываемый токен и
обращается к `/api/...` только с ним; cookie Пульса никогда не покидают сервер.
Список устройств и кнопка «отвязать устройство» в ЛК и админке.

**Этап 3 — отказ от переноса сессий между телефонами.** Убрать Nearby/QR-перенос
из клиента: доступ к аккаунту выдаёт сервер (вход через университет + пароль
страницы). Это устраняет самый опасный путь копирования секретов.

**Этап 4 — серверная история и расписание.** Отдавать расписание/группу и
историю посещений из сервера (кэш + ACS), чтобы телефон не ходил напрямую и не
кэшировал лишнего.

**Этап 5 — тонкий клиент.** Перевести мобильное приложение на обращение только к
нашему серверу по device-токену; оставить на телефоне лишь то, что требует
железа (NFC-диагностика).

## 6. Изменения в данных и API

- **Хранилище.** Добавить таблицы `device_tokens(token_hash, account_id,
  label, created, last_seen, expires)` и `audit_log(ts, actor, account_id,
  action, ip)`. Токены — только хэш (sha256), как уже сделано для сессий панели.
- **Отзыв.** `end_session` (этот релиз), `revoke_device`, массовый «завершить всё».
- **API доступа устройств (этап 2):** `POST /api/devices` (выдать токен после
  подтверждения через университет), `GET /api/devices` (список), `DELETE
  /api/devices/{id}` (отвязать). Все действия над аккаунтом — под токеном сессии
  страницы или device-токеном этого аккаунта, либо под админкой.
- **Единый слой авторизации.** Сейчас есть панель (пароль+CSRF) и сессия
  страницы. Свести к одному помощнику `require(account_id, who=...)`, чтобы не
  было открытых мутаций в `/api/`.

## 7. Безопасность: что улучшаем

Уже сделано в ходе работы: пароль на страницы, запрет захвата аккаунта без
сессии, разделение пулов браузера, разрешение на пропуск, авторизация действий.
Что стоит добавить:

1. **Закрыть открытый телефонный API.** Сейчас `GET /api/accounts`, события и
   часть мутаций открыты (модель «URL = доступ»). После этапа 2 — всё под
   device-токеном; снапшот без токена не отдаётся.
2. **Аудит-лог.** Кто/что/когда: входы, завершения сессий, выпуск пропуска,
   изменения группы. Нужен для расследования инцидентов.
3. **Лимиты по аккаунту, а не только по IP** (за Nginx все клиенты — один IP):
   лимитировать по токену/аккаунту.
4. **Жёсткий лимит памяти контейнера** (`mem_limit`/`deploy.resources`), чтобы
   всплеск браузера ронял только контейнер, а не хост (уже обсуждали).
5. **Бэкапы БД+ключа** по расписанию и проверка восстановления.
6. **Наблюдаемость:** `/metrics` (кол-во аккаунтов, состояния, ошибки продления),
   алерты на массовые expired.
7. **Миграция SQLite → PostgreSQL** при росте (сейчас один воркер и один файл —
   это предел; для класса ок, для масштаба нет).
8. **2FA/отдельный секрет для админки** и ограничение админ-панели по сети/VPN.
9. **Ротация `master.key`** и процедура компрометации (как перешифровать).
10. **Чёткая политика хранения ACS/истории** (сколько храним, что показываем).

## 8. Функция «Завершить сессию» (этот релиз)

Поведение: завершение **не удаляет** аккаунт (остаются имя, группа, пароль
страницы, разрешение пропуска), а делает сохранённую сессию Пульса
неработоспособной:

1. best-effort запрос к logout Пульса (`/api/auth/logout`) с текущими cookie,
   чтобы завершить SSO и на стороне МИРЭА;
2. удаление из зашифрованного секрета `cookie` и `storage_state`
   (и меток `expires_at`/`renewed_at`);
3. статус аккаунта → `expired`, инкремент версий, событие синхронизации (телефоны
   сразу перестают использовать сессию);
4. авто-продление для такого аккаунта не запускается (нет `storage_state`), пока
   владелец не войдёт заново.

Доступ: владелец на своей странице `/u/{id}` (под сессией страницы) и админ в
панели. Везде, где раньше читался `secret['cookie']`, добавлена проверка на
отсутствие сессии (возвращаем «сессия завершена», а не падаем).

## 9. Риски и откат

- **Совместимость с приложением.** Пока телефоны ещё «толстые», сервер должен
  продолжать отдавать текущий протокол; этапы 2–5 включаются вместе с обновлением
  клиента. Держим версию протокола и флаги включения.
- **Зависимость от Пульса.** Все серверные операции завязаны на доступность
  Пульса и действующий SSO; сервер не делает сессии вечными. Нужны понятные
  статусы и уведомления (бот уже есть).
- **Единая точка отказа.** Сервер теперь критичен: обязательны бэкапы, лимит
  памяти, перезапуск, мониторинг.
- **Откат.** Каждый этап — отдельный флаг; при проблеме выключаем флаг и
  возвращаемся к предыдущему поведению без потери данных (`.env` и том БД
  сохраняются).

## 10. Что делать прямо сейчас

1. Выкатить «Завершить сессию» (этот релиз) — база отзыва.
2. Включить аудит-лог и лимит памяти контейнера (малые изменения, большой эффект).
3. Спроектировать device-токены (этап 2) — это ядро «секреты только на сервере».
4. Согласовать отключение переноса сессий в клиенте (этап 3).
