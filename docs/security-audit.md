# Аудит безопасности — 7 ноября 2026

Область: Go-сервисы, авторизация, пользовательская видимость, браузерные
задания, ресурсные ограничения и штатный Docker Compose. Рабочий сервер
не сканировался. Это отчёт по найденным проблемам, а не гарантия отсутствия
всех уязвимостей и не результат независимого пентеста.

## Подтверждено при чтении кода

| ID | Риск до исправления | Условие / последствие |
| --- | --- | --- |
| S01 | Высокий: обход границ групп | Авторизованный пользователь мог находить людей по точному username и получать карточки через разрешения, даже без общего занятия |
| S02 | Высокий: ложная общая пара | Совпадения времени и физической аудитории хватало при разных предметах; могли открываться чужие люди и отметки |
| S03 | Высокий: неполный отзыв доступа | Основной сервис проверял JWT офлайн и не проверял отзыв AA ID-сессии; site-cookie могла жить 30 дней независимо от блокировки AA ID |
| S04 | Средний: срок/отмена QR-результата | Claim готового задания не проверял абсолютный срок; отмена готового задания не очищала результат сразу |
| S05 | Средний: ресурсный DoS | Нет общего предела одновременно обрабатываемых HTTP-запросов, до пользовательской квоты возможны обращения к БД |
| S06 | Средний: рост числа загрузок | Кеш ограничивал сохранённые календари, но не число одновременно запущенных загрузок разных групп |
| S07 | Средний: рост таблиц лимитеров | Фоновая очистка есть, но предел числа различных ключей/IP отсутствовал |
| S08 | Средний: временная привязка отметок | Сопоставление внешнего журнала с допуском 10 минут и локальных отметок только по времени не доказывает принадлежность чужой отметки конкретной паре |

Правило пользователя: свои одногруппники доступны в дневной таблице;
чужая группа появляется только если сегодня есть подтверждённая общая
пара. Имена такой группы можно показывать весь день. Её отметки доступны
только в столбцах совместных пар; остальные ячейки отсутствуют/пусты.
Разрешение на пропуск не отменяет ограничения видимости людей.

## Условные риски и пределы защиты

- При доступе к AA ID в обход доверенного nginx `TrustProxy` допускает
  подмену адреса для квот. Штатный Compose публикует порт на loopback,
  host nginx обязан перезаписывать X-Real-IP. Публичный прямой порт недопустим.
- Распределённые запросы QR-входа способны занять конечную очередь даже
  при корректных квотах. Для массового публичного запуска нужны внешний
  admission control/WAF либо доказательство присутствия человека.
- Компрометация хоста, административного пароля или ключей остаётся
  компрометацией соответствующей области. Зашифрованная БД без отдельной
  сохранности master.key не защищает от захваченного работающего процесса.
- Кеширование внешнего расписания и ошибки источника ограничивают точность
  решения об общей паре. При недостаточных/просроченных данных чужая группа
  должна скрываться. Совпадение аудитории без согласованного предмета не
  считается достаточным доказательством.
- Уже полученные законно имена/отметки пользователь может сохранить локально.
  Сервер может запретить будущую выдачу, но не стереть копию на чужом устройстве.
- Проверка исходников SQL не выявила подтверждённой инъекции: значения
  параметризованы; диагностические имена таблиц/столбцов сверяются и цитируются.
  Это не заменяет динамические и независимые проверки.

## Проверки исправлений

S01–S08 исправлены в коде 2.2.0:

- S01: общий серверный roster scope пересекается со всеми пользовательскими
  списками/поиском/разрешениями. В событиях остаются собственные аккаунты и
  адресованные пользователю изменения, без активности чужих аккаунтов.
- S02: время/предмет/преподаватель/тип/аудитория проверяются совместно.
  Преподаватель и предмет должны быть непустыми. Просроченное расписание
  не используется для допуска чужой группы, неопределённость закрывает доступ.
- S03: связка user/Pulse/session и текущая группа проверяются в PostgreSQL.
  Сервис sessions имеет только EXECUTE на две SECURITY DEFINER-функции
  с фиксированным search_path, без SELECT на AA ID-таблицы. Код callback
  привязан к живой исходной сессии. Старые site-cookie требуют нового входа.
- S04: абсолютный TTL проверяется и при claim готового задания; отмена и
  истечение сразу удаляют credentials/QR. Запоздалые обновления их не возвращают.
- S05: 128 одновременно обрабатываемых HTTP-запросов на сервис и максимум
  два long-poll на identity. При исчерпании — 429, а не новая очередь в памяти.
- S06: максимум 16 одновременных загрузок разных календарей, 20 секунд на
  загрузку; остаются ограничения размера ответа и общего кеша.
- S07: максимум 8192 ключа лимитера, очистка учитывает длительность окна;
  максимум 256 сохраняемых QR-заданий. IP из proxy нормализуется как IP.
- S08: новые локальные отметки хранят lesson_start; чужие старые отметки
  без привязки скрываются, внешний журнал чужой группы сопоставляется точно
  по началу, концу и предмету. Состояние турникета чужой группы не публикуется.

Регрессионные тесты проверяют дневные имена/отметки, несовместимые занятия,
границы окна ±30 минут, ранние отметки, блокировку/отзыв и удаление группы
при старом JWT/cookie, TTL/отмену QR и ограничение загрузок/HTTP.
Проверки выполняются только с синтетическими данными и локальным PostgreSQL.
Реальный MIREA/SSO и конфигурация production-хоста ими не проверяются.

Мониторинг в 2.2.0 не добавляет публичного управления хостом: только
приватная панель читает ограниченный по размеру файл агрегированных чисел.
Docker socket остаётся у host-only systemd-сборщика, который не слушает сеть.
Код и состояние сборщика устанавливаются в root-owned каталоги.
Итоги сети включают внутренний обмен и не равны биллингу провайдера.

## Проверка зависимостей

Первый govulncheck отметил [GO-2026-5932](https://pkg.go.dev/vuln/GO-2026-5932)
только на уровне модуля x/crypto: затронутый OpenPGP сервер не импортирует,
из модуля используется scrypt. Достижимых уязвимых функций не найдено.
Зависимость всё равно обновлена с v0.58.0 до исправленного коммита
v0.58.1-0.20261009181718-2f1f834330b2, указанного в официальной записи.
Это устранение предупреждения состава зависимостей, а не доказательство
прежней эксплуатации сервера.

Повторный govulncheck v1.9.0 на Go 1.26.10: `No vulnerabilities found`.
Docker builder закреплён на golang:1.26.10-bookworm, manifest проверен.
Полный `go test -race ./...` с четырьмя локальными PostgreSQL-базами на
Go 1.26.10 после обновления зависимости также прошёл.
Сканер отражает известные записи базы на момент проверки и не заменяет
анализ логики доступа и тестирование развёрнутой конфигурации.
